## Existing problems and alternatives

These sources establish real problem categories. They do not validate demand for these exact proposed products.

- [OpenRefine](https://openrefine.org/) already supports local data cleaning and repeatable transformations. ImportDesk targets a narrower browser-only, destination-schema import review. It should not attempt to replace OpenRefine's reconciliation ecosystem.
- [GOV.UK validation guidance](https://design-system.service.gov.uk/patterns/validation/) and [check-answers pattern](https://design-system.service.gov.uk/patterns/check-answers/) describe error recovery and review flows. FormPath packages these kinds of interactions for React developers while using its own visual identity; it is not government-approved software.
- [ODK Collect](https://docs.getodk.org/collect-intro/) explicitly supports offline field data collection. RepairRelay focuses on shared repair-case handoff and conflict review, not a general form collection platform. [ODK's submissions guidance](https://docs.getodk.org/central-submissions/) illustrates that collection and server submission are distinct operations.
- [Open Repair Alliance](https://openrepair.org/about/) and the [Open Repair Data Standard](https://standard.openrepair.org/standard.html) establish the repair-event recording context and a concrete export destination. The proposed handoff workflow still needs organiser validation; existing recording tools are alternatives to compare, not evidence that no solution exists.
- [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md) already offers measurement assertions and build comparison. ReleaseProof adds a portable review packet combining performance, accessibility and visual evidence. It consumes existing tool outputs rather than implementing another browser audit engine.

Before starting, speak with prospective users about the last time the problem occurred and compare their current tool. If the proposed product adds no meaningful benefit, contribute an improvement upstream or change the narrow workflow. The plans include stop/pivot criteria.

## Interpretation and uncertainty

The architecture, product names, scope, estimates, budgets and acceptance tests in this folder are original planning recommendations. No interviews, benchmark runs, package publication, user testing or production deployments have happened as part of this work. Quantitative targets are acceptance goals, never claimed results. Recheck service terms, job availability, dependency support and package-name availability at implementation time.
